# PRD v3.0 — Ревизија на PRD v2.0 + Design Handoff и спецификација за сениор девелопери

2026-09-22 · Ревизија: Senior Product Owner · Статус: **чека потврда на одлуките D-1…D-12, потоа се спојува во чист PRD v3.0**

Овој документ **не го заменува PRD v2.0 во целост** — го надградува. Секоја секција подолу кажува кои делови од v2.0 и од Handoff README ги **прегазува**. Девелоперите читаат: (1) овој документ, (2) PRD v2.0 за сè што овде не е споменато, (3) Handoff README само за визуелен дизајн (токени, распоред, копи) — **не** за податочен модел и логика, освен каде што овде е потврдено.

---

## 0. Заклучок од ревизијата

PRD v2.0 е добар **процесен** документ: улогите, работниот тек, календарот и принципите се јасни и одговараат на реалната работа. Но за сениор девелопери да го искуцаат **без грешка**, не е доволен, поради три групи проблеми:

| Група                                                                                                  | Број | Ефект ако не се реши                                                                               |
| ------------------------------------------------------------------------------------------------------ | ---- | -------------------------------------------------------------------------------------------------- |
| A. Контрадикции PRD ↔ Handoff (прототипот имплементира различна логика од PRD)                         | 11   | Девелоперот ќе избере едната верзија, дизајнерот другата — системот ќе „работи“ и ќе биде погрешен |
| B. Недефинирано во PRD (концепт постои, правило нема)                                                  | 14   | Секој девелопер ќе ги пополни дупките поинаку                                                      |
| C. Недостасуваат технички спецификации (state machine, API, шема, векторски слој, редослед на градење) | —    | Нема единствен извор на вистина; логиката ќе се дуплира во UI, API и автоматизации                 |

Најважниот принцип за v3.0: **една табела на статуси, една матрица на преоди, една функција за покриеност, една функција за дозволи — дефинирани во код на едно место (`packages/core`) и користени од API, UI, Board drag-and-drop, Rule Builder и ботот.** Прототипот ја научи истата лекција (README, „Derive, never store“) — ја подигаме на ниво на архитектура.

### 4.3 State machine — единствен модул

**Правило за архитектура:** матрицата живее во `packages/core/src/workflow/transitions.ts` како податок (не како `if` гранки) и се увезува од: API (`POST /tasks/:id/transition`), Board drag-and-drop валидација (клиент-страна, само за UI feedback — серверот пак проверува), Rule Builder (акција „Промени статус“) и извозот за ботот (§4.12). **Забрането** е кој било друг модул да менува `status` директно.

Секој преод: `{ from, to, contentType, actor: role | 'system', guards: Guard[], effects: Effect[] }`. Преодот се извршува во **една DB трансакција**: провери guards → промени статус → изврши effects → запиши EventLog → outbox настан за real-time и знаење.

**Guards** (сите враќаат `{ ok } | { ok:false, code, missing: string[] }`; пораката за корисник се гради од `missing` на македонски):

| Guard                       | Проверува                                                                                 |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| `G_ROLE`                    | актерот има улогата од редот, или е Директор (D-5, со `reason`)                           |
| `G_ASSIGNEE_REQUIRED(role)` | таскот има доделен вработен со таа улога                                                  |
| `G_NOT_SELF_APPROVAL`       | Монтажер ≠ Режисер на таскот; Дизајнер ≠ Гр. креатор на таскот                            |
| `G_FILE(kind, minCount)`    | постои `FileAsset` од тој вид на таскот/капата (`final`, `graphic`, `raw`, `scenarioDoc`) |
| `G_COMMENT`                 | `payload.comment` не е празен (враќања и „одобрено со измени“)                            |
| `G_TEXT(field, minChars)`   | брифинг ≥ 50 знаци; копи ≥ 1 знак                                                         |
| `G_PUBLICATION`             | барем една `Publication` со платформа, тип и линк                                         |
| `G_CAPA_FIELDS`             | сценарист, датум, час, место, насоки — сите 5                                             |
| `G_SCENARIOS_SPLIT(min 1)`  | документот е поделен на ≥ 1 сценарио со статус `predlozeno`                               |
| `G_SCENARIO_OUTCOMES`       | секое сценарио има исход                                                                  |
| `G_META_ADS`                | `client.usesMetaAds`                                                                      |
| `G_DECISION`                | Promotion.decision внесена; ако `paid` → кампањата е `closed`                             |
| `G_SLOT_FREE`               | целниот слот е `free` и не е во минатото                                                  |

**Effects:** `E_ASSIGN(role)` (од `payload.assigneeId` или `client.defaultAssignees[role]` или глобален default), `E_VERSION_BUMP` + `E_REVISION(source)`, `E_APPROVAL(type)`, `E_ACTIVATE_CHILDREN`, `E_CLOSE_GROUP`, `E_BIND_SCENARIOS`, `E_CREATE_EXTRA_SLOTS`, `E_RELEASE_SLOT`, `E_NOTIFY(key, recipients)`, `E_ALARM(key)`, `E_SCHEDULE_METRICS`, `E_STORAGE_TIMER`, `E_AUTO_NEXT(to)` (системски преод во иста трансакција).

### 4.5 Слотови и календар (го дополнува PRD §4)

**Алгоритам за рамномерно распоредување** (детерминистички, тестабилен):

```
D = сортирани дозволени датуми во месецот за (клиент, тип): weekdays од CalendarConfig минус Holiday (global + client)
m = |D|, n = бараната количина
ако n ≤ m:  избери D[ floor((i + 0.5) * m / n) ] за i = 0..n-1      // 4 во 9 дена → индекси 1,3,5,7
ако n > m и allowTwoPerDay: сите m дена orderInDay=1, потоа (n−m) дена со orderInDay=2 по истата формула врз D; аларм до АМ, слотовите со orderInDay=2 бараат рачна потврда
ако сè уште недостасува: остатокот → следен месец со carriedFromMonth, обележан во предлогот
```

**Животен циклус на слот:** `predlog` (генериран, уредлив без причина) → `reserved` (потврден месец; се креира мртов таск) → `used` (таскот објавен) ; `reserved` → `free` (таскот преместен/паузиран/откажан → црвен во календар) ; `free` + датумот помина → `missed`.

**Генерирање:** BullMQ repeatable job `slots.generate`, cron `0 6 20 * *` (Europe/Skopje), идемпотентен по (клиент, месец): ако постојат слотови за тој месец, не прави ништо. При активација на клиент — за тековниот и следниот месец.

**Потврда на месец** (`POST /clients/:id/slots/confirm`, само `am`/`dir`): сите `predlog` → `reserved`, се креираат `Task(status=mrtov)` по слот и `TaskGroup` по тип (ако нема). Клиент со `calendarType = specificen`: слотовите се внесуваат рачно во истиот екран, истата потврда.

**Промена на датум** (`POST /tasks/:id/date-change {newDate, orderInDay?, reason}`): дозволено `dir`, `am`, `rez` (само видео), `krea` (само графика); `newDate ≥ денес`; целниот слот мора да е `free` или се креира нов ако датумот е дозволен по календарот; стариот слот → `free`; `DateChange` + EventLog; насловот се регенерира ако `titleIsAuto`. Не смее на таск во `objaveno`/`analitika`/`zavrseno`/`otkazano`.

### 4.6 Активација — прецизно

**Видео (при `scenKajKlient → snimanje`):** одобрените сценарија (`odobreno` + `odobrenoSoIzmeni`) се сортираат по `ordinal`; мртвите деца на капата по датум на слот. Се врзуваат 1:1 (`Task.scenarioId`), статус → `cekaSnimanje`, `rezId` = режисерот на капата, `assigneeId` = камерманот. Ако одобрени < мртви: вишокот останува `mrtov` (црвен), аларм 9 до Директор. Ако одобрени > мртви: за секое дополнително сценарио се бара следен слободен видео-датум (алгоритам §4.5 за 1 слот, почнувајќи од денес), се креира слот + таск со `isExtra = true`; аларм 9 до Директор и АМ.

**Видео (при прикачување суров материјал):** системски преод капа → `zatvoren`; сите деца во `cekaSnimanje` → `chekaRezija`, `assigneeId` = режисер. Датумите **не се менуваат**.

**Графика:** секој мртов таск поединечно `mrtov → brifing` кога креаторот ќе го отвори и кликне „Започни брифинг“; или bulk „Активирај ги сите слотови“ од капата. Првиот таков преод ја затвора капата. `brifing → dizajn` бара текст ≥ 50 знаци и дизајнер. Датумите не се менуваат.

### 4.7 Одговор од клиент за сценарија (го дополнува PRD §8)

Во капа панел, статус `scenKajKlient`, Режисерот за секое сценарио избира: Одобрено · Одобрено со измени (коментар задолжителен) · Отфрлено (коментар задолжителен). Копче „Заврши одговор“: ако ≥ 1 одобрено → преод кон `snimanje`; ако 0 одобрено → преод кон `scenarija` (враќање), документот добива нова верзија, отфрлените остануваат во историја со коментарот. Секој исход = `Approval(objectType=scenario, source=employee, channel)`; опционален screenshot.

### 4.8 Објава по платформа и `metaMediaId`

`Publication` е една **по платформа** (еден таск може да има FB + IG). Преодот `zaObjavuvanje → objaveno` бара ≥ 1 публикација со линк. Извлекување на `externalRef` од `permalink`:

| Шема                                                                                                      | externalRef                                     |
| --------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `facebook.com/{page}/posts/{id}` · `/videos/{id}` · `/reel/{id}` · `photo/?fbid={id}` · `story_fbid={id}` | нумерички `id`                                  |
| `instagram.com/p/{code}` · `/reel/{code}`                                                                 | `code` (shortcode)                              |
| `tiktok.com/@{user}/video/{id}`                                                                           | `id` (само евиденција; нема метрики во Фаза B2) |

Worker `publication.resolve`: за FB `metaMediaId = pageId_postId`; за IG се бара во `GET /{ig-user-id}/media?fields=permalink,shortcode` и се совпаѓа по shortcode. Неуспех → `resolveStatus = failed`, аларм до АМ, рачен внес на `metaMediaId` (`manual`).

### 4.9 Покриеност — единствена функција

```

readyCoverage(client, type)   = max(slot.date за таскови со status ∈ {zaObjavuvanje, objaveno, analitika, zavrseno}) − денес
clientCoverage = min(plannedCoverage video, plannedCoverage graphic), само за типовите со количина > 0
```

Алармот 10 и лентите во боја користат `plannedCoverage` со праг `client.coverageAlarmDays`. `readyCoverage` се прикажува во Преглед како „готово до {датум}“. Прагови за боја: > 14 зелено, 7–14 портокалово, < 7 црвено.

### 4.10 Рокови по статус

`StatusDeadlineConfig` со seed од §4.1/§4.2. Резолуција: по клиент → глобално. `deadlineFor(task) = publishDate − leadDays(status)`; за капа: `shootDate − leadDays`. Ако нема `shootDate` уште — нема рок. Етикети по Handoff („рок пречекорен N дена / рок денес / рок утре / рок за N дена“, еднина „1 ден“). Уредливо во Админ → Автоматизации → „Рокови по статус“.

### 4.12 Векторски слој — целиот систем читлив за бот (го заменува PRD §16)

Цел: бот (Claude помошник, Фаза B4) да одговара на **„што се случува и зошто“** (историја, коментари, сценарија, брифинзи, одлуки на клиент, правила на процесот) од векторската база, и на **„каков е статусот сега“** од живата база. Двете се одвоени намерно — статус од застарен ембединг е погрешен одговор.

#### Ентитет

```prisma
model KnowledgeChunk {
  id            String   @id
  sourceType    KnowledgeSource   // clientProfile | scenario | brief | copy | clientFeedback | internalFeedback |
                                  // comment | eventNarrative | metricSummary | processDoc | ruleDoc
  sourceId      String            // id на изворниот запис
  clientId      String?
  taskId        String?
  groupId       String?
  visibility    Visibility        // internal | clientVisible   (Фаза D: клиентската PWA гледа само clientVisible)
  occurredAt    DateTime          // време на изворот, за временски филтер
  text          String            // ≤ 800 токени, преклоп 100 при делење
  metadata      Json              // { status, role, actorId, contentType, month, outcome, version … }
  contentHash   String            // sha256(text) — дедупликација и „stale“ детекција
  embedding     Unsupported("vector(EMBED_DIM)")?
  tsv           Unsupported("tsvector")?          // GENERATED од text, config 'simple' + unaccent
  embeddingStatus EmbStatus       // pending | done | failed | stale
  embeddingModel  String?
  @@index([clientId, sourceType, occurredAt])
  @@unique([sourceType, sourceId, contentHash])
}
```

Индекси: `CREATE INDEX ON knowledge_chunk USING hnsw (embedding vector_cosine_ops) WITH (m=16, ef_construction=64)`; GIN на `tsv`. `EMBED_DIM` е фиксиран пред првата миграција (**D-10**). Дополнително, изворните табели `Client.notes`, `Scenario.body`, `Task.brief`, `Task.copy`, `Revision.comment`, `Approval.comment`, `Comment.body` добиваат `embeddingStatus` за backfill контрола (PRD §16), но **ембедингот се чува само во `KnowledgeChunk`** — една табела за пребарување, не десет.

#### Што се индексира и кога

| sourceType       | Извор                                                                                                        | Кога                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| clientProfile    | Client.name + notes + бројки од договорот + канал + модули                                                   | при секоја измена на клиент              |
| scenario         | Scenario наслов + хук + текст + исход + коментар од клиент                                                   | при поделба и при секој исход            |
| brief            | Task.brief + имиња на референци                                                                              | при зачувување брифинг                   |
| copy             | Task.copy + платформи + тип                                                                                  | при `objaveno`                           |
| clientFeedback   | Approval(type=client).comment + исход + верзија                                                              | при внесување одговор — **највредно**    |
| internalFeedback | Revision(source=internal).comment                                                                            | при враќање                              |
| comment          | Comment.body                                                                                                 | при коментар                             |
| eventNarrative   | EventLog.narrative                                                                                           | при **секој** настан                     |
| metricSummary    | месечен текстуален резиме по објава и клиент (бројки во реченици)                                            | по секое влечење (агрегиран job, дневно) |
| processDoc       | извоз на §4.1–4.3 (статуси, матрица, guards), §2 дозволи, §4.9 покриеност — генериран од **кодот**, не рачно | при секој deploy                         |
| ruleDoc          | AutomationRule + StatusDeadlineConfig во реченици                                                            | при секоја измена на правило/рок         |

**Наратив на настан** (`EventLog.narrative`): детерминистички шаблон по `eventType`, на македонски, без LLM, генериран во истата трансакција. Пример: _„Дејан Т. (Монтажер) го премести таскот „Астибо · Видео · 25.09“ од Монтажа во Внатрешно одобрување на 22.09.2026 во 14:10 (верзија 2).“_ Шаблоните се во `packages/core/src/events/narratives.ts` и се задолжителни за секој нов `eventType` (тест: секој enum член има шаблон).

#### Пајплајн

`EventLog` → `Outbox(kind=knowledge)` → BullMQ `knowledge.index` (retry 5, backoff) → chunk → `contentHash` дедуп → embedding API → `done`. Измена на извор → стариот chunk `stale` (се брише од резултати, не од база), нов `pending`. Backfill job за постоечки податоци при Фаза B4 (serijski, 500/минута). Неуспех на embedding провајдер не блокира ништо во работниот тек.

#### Пребарување и ACL

`POST /knowledge/search { query, clientId?, taskId?, sourceTypes?, since?, k=12 }` → хибридно: top-30 по cosine + top-30 по `ts_rank` → Reciprocal Rank Fusion → k. **ACL:** се применува истата `scope` функција како за List (`own` улога гледа само chunks на свои таскови; `all` гледа сè; `clientVisible` филтер за Фаза D). Резултатот носи `sourceType`, `occurredAt`, линк до таскот.

#### Договор за ботот (Фаза B4)

`POST /assistant/ask { question, taskId?, clientId? }`. Системски промпт = `processDoc` + `ruleDoc` chunks (секогаш) + профил на клиентот (ако има контекст). Алатки: `knowledge.search` (историја, зошто) и `task.getState(taskId)` / `client.getOverview(clientId)` (живо: статус, доделен, рок, покриеност). Ботот **не пишува** ништо во Фаза B4. Секој одговор наведува извори (taskId + датум). Одговорот е на македонски.

### 4.13 Известувања

`Notification.dedupeKey = {eventKey}:{taskId|groupId|clientId}:{recipientId}:{YYYY-MM-DD}` → ист аларм за ист објект не се повторува во 24 ч (PRD §13). Канали по ниво: потсетник = in-app; аларм = in-app + email; критичен = in-app + email + Viber (Директор) + модал што бара „Видено“. Дневен преглед за Директор: job `notifications.digest` во 07:00. Вработен може да исклучи само `potsetnik`.

Сите 15 настани од PRD §13 се **системски `AutomationRule` (`isSystem = true`)**: видливи и вклучливи во Админ → Аларми, не се бришат. Настаните 12–15 (токен, метрики, недозволен преод, сторидж) се технички и се емитираат од worker-ите, но исто така се водат како записи во истата табела заради униформност.

## 7. Инструкции за сениор девелоперите (се додаваат на почетокот на PRD v3.0)

1. **Читај по ред:** овој документ → PRD v2.0 → Handoff README (само визуелно) → `GoDigital Task Manager.dc.html` за копи и распоред. Не читај `support.js`.
2. **Од прототипот се порта:** токени, распоред, копи (кирилица, финални), состојби на компоненти, `ROLE_CFG.nav`, `ST` бои. **Не се порта:** `absDay`, `m: 'sep'|'oct'`, `freeSlotsFor`, `capActivate`, `STEP_LEAD` како константа, `DEFAULT_ASSIGNEES` како глобал, seed податоци како фикстур.
3. **Едно место за логика:** статуси, преоди, guards, дозволи, покриеност, рокови, наративи — во `packages/core`. Ако ти треба `if (status === …)` надвор од `core`, тоа е сигнал дека недостасува функција во `core`.
4. **Ништо не се брише, ништо не се презапишува** од EventLog, MetricSnapshot, Revision, Approval — спроведено со DB привилегии.
5. **Секој преод е трансакција** со guards → промена → effects → EventLog → Outbox. Нема преод без EventLog, нема EventLog без наратив.
6. **Серверот одлучува.** UI крие копчиња, серверот одбива повици. Тест за секој ред од матрицата дека погрешна улога добива `FORBIDDEN_ROLE`.
7. **Копи е финално и на кирилица.** Ниту еден стринг во компонента; сè низ i18n со плурали.
8. **Кога PRD и Handoff се косат** и не е покриено овде — стоп, прашање до Product Owner, не претпоставка.
9. **Фазите се затворени.** Идеја надвор од тековната фаза оди во „Фаза 2+ листа“ во `docs/backlog.md`, не во sprint.
