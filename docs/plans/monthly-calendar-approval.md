# План: Месечно одобрување на календар (АМ) + тврд гејт за капа

Статус: **ПРЕДЛОГ — чека одобрување.** Не е имплементирано.

## Барања (сопственик)

1. АМ одобрува **СТАНДАРДЕН календар за секој месец** (кој ден видео, кој ден графика).
2. **Пакети/комбинации** — фиксни бројки:
   - Графики/мес: 8, 10, 12, 16, 24, 30
   - Видеа/мес: 2, 3, 4, 5, 6, 8, 12
     Клиент = комбинација (V видеа + G графики). Клиентот „влече" по бројот на видеа/графики.
3. За секој месец мора да има **комбинација (V,G) + точни денови на објавување**, цел месец пополнет.
4. АМ ги организира по своја логика → може да ги **одобри сите комбинации за месецот**.
5. Системот секогаш дава **пополнет предлог**; АМ само менува.
6. АМ може да организира **повеќе месеци однапред**.
7. **Тврд гејт:** ако месецот не е организиран + **одобрен**, капа-таск не смее да повлече датуми од
   тој месец → прво **извести го АМ** да ги одобри датумите → потоа Режисер креира капа.
8. Одобрувањето важи за **сите клиенти со СТАНДАРДЕН календар**; + копче за **CUSTOM по клиент**
   (иста бројка V/G, само други денови).

## Што веќе постои (да не дуплираме)

- `CalendarConfig` (стандарден `clientId=null` + посебен по клиент) = **неделни денови** по тип
  (видео/графика) + време. Editor веќе е на екранот Календар („Календарски поставки").
- `generateSlots` (core) = **детерминистичко рамномерно распоредување** на N единици по неделни
  денови во месец → готов „предлог".
- `PublishingSlot` (`predlog → reserved → used`) = конкретните датуми по клиент по месец.
- `confirmMonth` = `predlog→reserved` + мртви таскови + **авто-капа (D-7)**.
- `clientActiveForDate` (деактивација) + мек гејт `isClientApprovedForMonth`.

## Клучен увид

**„Одобрен месец за клиент" = клиентот има `reserved` слотови за тој месец.** Предлог=`predlog`
слотови; уредување=влечење (веќе постои H1); одобрување=`confirmMonth`. Значи 80% од механиката
постои — недостасуваат: (а) одобрување за **сите стандардни клиенти наеднаш**, групирано по
комбинација; (б) **тврд гејт + известување** наместо мек; (в) секогаш пополнет предлог.

## Препорачан модел (моја препорака)

Не воведувам нов „combination" ентитет. Наместо тоа:

1. **Стандарден календар по тип** (постои): АМ поставува кои неделни денови се видео / графика +
   време. Ова е основата за предлогот.
2. **Месечно одобрување (ново)** — екран „Календар → Одобри месец":
   - АМ бира месец (може однапред).
   - Системот покажува **предлог за целиот месец**, генериран за секоја комбинација (V,G) што
     ја имаат стандардните клиенти (преку `generateSlots` со стандардните денови + бројките).
     Приказ **групиран по комбинација** (пр. „4 видеа · 12 графики → овие датуми"), за да АМ
     одобрува по комбинација, не по секој клиент.
   - АМ менува денови (влечење), потоа **„Одобри месец"** → за сите стандардни клиенти со таа
     комбинација се креираат `reserved` слотови (+ мртви таскови/авто-капа, D-7).
3. **CUSTOM по клиент** (постои editor): иста бројка V/G, други денови; неговите слотови се
   генерираат/одобруваат посебно.
4. **Тврд гејт (ново, заменува мек):** креирање капа / активација / екстра таск / промена датум
   што паѓа во месец **без `reserved` слотови (неодобрен)** →
   - **блокирано** со `MONTH_NOT_APPROVED`,
   - **аларм до АМ**: „Одобри го календарот за {клиент} · {месец}",
   - дури по одобрување Режисер може да креира капа.
5. **Секогаш пополнет предлог:** при отворање месец што нема слотови, автоматски се пресметува
   предлог (не се снима додека АМ не одобри).

### Зошто ова е подобро од посебен „combination" ентитет

`generateSlots` веќе прави точен распоред по бројка. Клиентите со иста комбинација + исти
стандардни денови добиваат идентичен релативен распоред → „одобрување по комбинација" се сведува
на групиран приказ, без дупло складирање. Помалку шема, помалку багови, иста цел.

## Одлуки (сопственик одобри)

1. **Гранулација = (A) групирано по комбинација**, слотовите по клиент. Без нов ентитет.
2. **Гејт = тврд само за нови капи** (createVideoCapa) — блок + аларм до АМ. Историски/демо не се кршат.

## „Одобрен месец за клиент" (дефиниција)

= клиентот има **`reserved`** слотови за тој месец. Одобрувањето (`approveMonthForAllStandard` /
`confirmMonth`) создава reserved слотови. `predlog` (само предлог) НЕ е одобрено.

## Чекори за градење (по одобрување)

1. core: помошник за „комбинации во употреба" + предлог-распоред по комбинација (чиста функција,
   тестови).
2. api: `getMonthProposal(month)` (групирано по комбинација) + `approveMonthForAllStandard(month)`;
   тврд гејт во `createVideoCapa`/`createExtraTask`/`changeTaskDate`/активација + аларм до АМ.
3. web: екран/секција „Одобри месец" со групиран предлог + уредување + „Одобри".
4. тестови: гејт (блок+аларм), одобрување создава reserved за сите комбинации, custom override.
